# MCP Wrapper Demo Guide
**How to Present the Jensen Hughes Craft CMS + Botpress AI Integration**

---

## 📋 Executive Summary (30 seconds)

**What it is:** A bridge that lets AI assistants (like Botpress bots) directly query and interact with Craft CMS content using the Model Context Protocol (MCP) - an open standard for AI-to-data connections.

**What it does for Jensen Hughes:** Their website visitors can ask an AI chatbot natural language questions like "Where's your California office?" or "Tell me about fire protection services" and get accurate, real-time answers pulled directly from their Craft CMS content.

**Key benefit:** No manual knowledge base maintenance. When content is updated in Craft CMS, the AI assistant automatically has access to the latest information.

## 🔧 Technical Implementation Details (READ THIS FIRST)

### Where Do the Tools Live?

**CRITICAL UNDERSTANDING:** The tools are **generated inside the plugin** by introspecting the GraphQL schema. They do NOT exist in Craft CMS natively.

```
┌────────────────────────────────────────────────────────┐
│  Craft CMS                                             │
│  • Has sections (News, Services, Offices)              │
│  • Has GraphQL API that exposes these sections         │
│  • Does NOT know about MCP or "tools"                  │
└────────────────────────────────────────────────────────┘
                         ↓
         (GraphQL Schema Introspection)
                         ↓
┌────────────────────────────────────────────────────────┐
│  MCP Wrapper Plugin                                    │
│  • Reads GraphQL schema                                │
│  • GENERATES tool definitions (query_services, etc.)   │
│  • Stores them in memory/cache                         │
│  • Tools are VIRTUAL - they're metadata, not code      │
└────────────────────────────────────────────────────────┘
                         ↓
         (Exposes via JSON-RPC)
                         ↓
┌────────────────────────────────────────────────────────┐
│  AI Clients (Botpress, Claude, etc.)                   │
│  • Discover tools via MCP protocol                     │
│  • Call tools with arguments                           │
│  • Get back formatted content                          │
└────────────────────────────────────────────────────────┘
```

**Key Point:** Tools are **metadata descriptors** generated from GraphQL schema, not executable code stored somewhere.

### Execution Flow: Request → Response (Step-by-Step)

#### Phase 1: Initialization (Happens Once)

```php
// 1. Plugin loads (on Craft startup or schema change)
McpWrapper::init()
  → Registers event listeners
  → Event::on(Gql::EVENT_AFTER_SAVE_SCHEMA) // Listen for GraphQL changes

// 2. GraphQL schema is saved/changed
EventHandler triggered
  → ManifestBuilderService::buildAndCacheManifest($schemaHandle)
    
    // 2a. Introspect GraphQL
    → introspectGraphQL($token)
      • HTTP POST to /api with GraphQL token
      • Query: { __schema { queryType { fields { ... } } } }
      • Returns: All queryable types (sections) and their fields
    
    // 2b. Parse schema
    → parseSchemaTypes($schemaData)
      • Loop through each entry type (e.g., "services_services_Entry")
      • Extract section handle: "services"
      • Extract fields: title, description, icon, etc.
      • Extract field types: PlainText, Number, Date, Entries, etc.
    
    // 2c. Generate tool definitions
    → generateToolForSection($sectionHandle, $fields)
      • Create tool object:
        {
          "name": "query_services",
          "description": "Query entries from Services section",
          "inputSchema": {
            "type": "object",
            "properties": {
              "search": {"type": "string"},
              "limit": {"type": "integer", "default": 10},
              "offset": {"type": "integer", "default": 0},
              "id": {"type": "integer"}
            }
          }
        }
    
    // 2d. Map field types
    → mapFieldType('PlainText') → 'string'
    → mapFieldType('Number') → 'integer' or 'number'
    → mapFieldType('Date') → 'datetime'
    → mapFieldType('Entries') → 'relation' (with source handles)
    
    // 2e. Cache to filesystem
    → file_put_contents(
        storage/runtime/mcp/manifest-ai.json,
        json_encode($manifest)
      )
```

**What Gets Cached:**
```json
{
  "schema": "ai",
  "timestamp": "2026-01-13T10:30:00Z",
  "tools": [
    {
      "name": "query_services",
      "description": "Query entries from Services section",
      "inputSchema": { /* JSON Schema */ }
    },
    {
      "name": "query_officeLocations",
      "description": "Query entries from Office Locations section",
      "inputSchema": { /* JSON Schema */ }
    },
    // ... one tool per section
  ]
}
```

#### Phase 2: Runtime (Every AI Request)

```php
// 1. AI client sends HTTP request
POST /actions/mcp-wrapper/mcp/index?schemaHandle=jensenhughes
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "query_officeLocations",
    "arguments": {"search": "California", "limit": 100}
  }
}

// 2. Request hits Craft router
Craft's routing system
  → Matches pattern: /actions/mcp-wrapper/mcp/<action>
  → Routes to: McpController::actionIndex()

// 3. McpController receives request
McpController::actionIndex($schemaHandle = 'jensenhughes')
  • Get request body: $payload = Craft::$app->request->getRawBody()
  • Parse JSON: $request = json_decode($payload, true)
  • Extract: $method = $request['method'] // 'tools/call'
  • Extract: $params = $request['params']
  
  → Delegate to McpServerService::handleRequest($method, $params, $schemaHandle)

// 4. McpServerService processes request
McpServerService::handleRequest($method, $params, $schemaHandle)
  
  // 4a. Load cached manifest
  → loadManifest($schemaHandle)
    • Read: storage/runtime/mcp/manifest-jensenhughes.json
    • Parse JSON into array
    • Store in $this->manifest property
  
  // 4b. Route by method
  switch ($method) {
    case 'tools/list':
      → return $this->manifest['tools']; // Just return tool definitions
    
    case 'tools/call':
      → executeToolCall($params['name'], $params['arguments'])
  }

// 5. Execute tool call
executeToolCall('query_officeLocations', ['search' => 'California', 'limit' => 100])
  
  // 5a. Validate tool exists
  → $tool = findToolInManifest('query_officeLocations')
    • If not found: throw error "Tool not found"
  
  // 5b. Validate arguments against schema
  → validateArguments($params['arguments'], $tool['inputSchema'])
    • Check types match
    • Check required fields present
    • Check ranges/constraints
  
  // 5c. Extract section handle from tool name
  → $section = extractSectionHandle('query_officeLocations') // 'officeLocations'
  
  // 5d. Build GraphQL query dynamically
  → $query = buildGraphQLQuery($section, $arguments)
  
  // THIS IS KEY: Query is built at runtime, not stored
  $query = <<<GRAPHQL
  query {
    entries(
      section: "officeLocations",
      search: "California",
      limit: 100
    ) {
      id
      title
      url
      ... on officeLocations_officeLocations_Entry {
        addressLine1
        city
        state
        zipCode
        phoneNumber
        hoursOfOperation {
          ... on hoursOfOperation_BlockType {
            dayOfWeek
            openTime
            closeTime
          }
        }
      }
    }
  }
  GRAPHQL;
  
  // 5e. Execute GraphQL query
  → $token = getTokenForSchema('jensenhughes') // From config
  → $result = Craft::$app->gql->executeQuery($query, null, null, $token)
  
  // OR via HTTP (if not using Craft's internal GQL):
  → $client = new GuzzleHttp\Client();
  → $response = $client->post('https://site.com/api', [
      'headers' => ['Authorization' => "Bearer $token"],
      'json' => ['query' => $query]
    ]);
  → $result = json_decode($response->getBody(), true);
  
  // 5f. Format response
  → formatMcpResponse($result['data']['entries'])
    • Convert GraphQL result to human-readable text
    • Or keep as structured data
    • Wrap in MCP content blocks

// 6. Return JSON-RPC response
return [
  'jsonrpc' => '2.0',
  'id' => $request['id'],
  'result' => [
    'content' => [
      [
        'type' => 'text',
        'text' => 'Found 2 offices in California: ...'
      ]
    ]
  ]
];

// 7. McpController sends HTTP response
return $this->asJson($response);
  → Craft serializes to JSON
  → HTTP 200 OK
  → Content-Type: application/json
  → Body: { "jsonrpc": "2.0", "id": 1, "result": {...} }

// 8. AI client receives response
Botpress/Claude receives JSON
  → Parses result
  → Extracts text from content blocks
  → Presents to user or uses for next decision
```

### Memory & Performance Characteristics

**Initialization (Cold Start):**
- ManifestBuilder introspects GraphQL: **1-3 seconds**
- Parses schema types: **100-500ms**
- Generates tool definitions: **50-100ms**
- Writes to cache file: **10-50ms**
- **Total: 2-5 seconds** (only happens on schema changes)

**Runtime (Hot Path):**
- Read cached manifest from file: **5-10ms**
- Parse JSON: **1-5ms**
- Validate arguments: **<1ms**
- Build GraphQL query string: **<1ms**
- Execute GraphQL query: **100-500ms** (depends on Craft/DB)
- Format response: **1-10ms**
- **Total per request: 150-550ms**

**Memory Usage:**
- Plugin code: ~2-3MB
- Cached manifest (in memory): ~100KB-1MB
- Per-request overhead: ~1-3MB
- GraphQL query execution: ~5-20MB (Craft's overhead)

**Scalability:**
- **Bottleneck:** GraphQL query execution in Craft (database queries)
- **Not a bottleneck:** MCP protocol overhead (<5% of total time)
- **Scaling strategy:** 
  - Add database read replicas
  - Cache GraphQL results in Redis
  - Use CDN for manifest endpoint

### What Happens When Things Change

**Scenario 1: Content Editor Updates an Entry**
```
Editor saves "San Diego Office" entry
  → Craft saves to database
  → Craft clears element caches
  → MCP Wrapper is NOT involved (no manifest rebuild)
  → Next AI query hits GraphQL → gets updated data automatically
```
**Result:** AI sees new data immediately (no cache to clear)

**Scenario 2: Admin Changes GraphQL Schema Permissions**
```
Admin removes "services" section from GraphQL schema
  → Craft saves schema
  → Triggers: EVENT_AFTER_SAVE_SCHEMA
  → MCP Wrapper rebuilds manifest
  → Manifest no longer includes "query_services" tool
  → Next AI query to tools/list → doesn't see "query_services"
```
**Result:** Tools auto-update when permissions change

**Scenario 3: Developer Adds New Section**
```
Developer creates "Team Members" section
  → Adds to GraphQL schema permissions
  → Craft saves schema
  → Triggers: EVENT_AFTER_SAVE_SCHEMA
  → MCP Wrapper introspects schema
  → Finds new "teamMembers" type
  → Generates "query_teamMembers" tool
  → Caches updated manifest
```
**Result:** New tool available automatically

**Scenario 4: Admin Rotates GraphQL Token**
```
Admin generates new token in Craft CP
  → Updates .env file: GQL_AI_TOKEN=new_token
  → Rebuilds manifest (uses new token for introspection)
  → Old token stops working
  → AI requests with old config fail
  → AI admin updates config with new token
```
**Result:** Token rotation requires config update on AI side

### Common Misconceptions

❌ **WRONG:** "Tools are stored in the database"
✅ **CORRECT:** Tools are generated from GraphQL schema and cached as JSON files

❌ **WRONG:** "Each tool is a PHP method that gets called"
✅ **CORRECT:** Tools are metadata. The same executeToolCall() method handles all tools by building GraphQL queries dynamically

❌ **WRONG:** "The plugin stores content"
✅ **CORRECT:** The plugin only stores tool definitions. Content comes from Craft's database via GraphQL

❌ **WRONG:** "I need to write code for each new section"
✅ **CORRECT:** Add section to GraphQL schema → tool auto-generates

❌ **WRONG:** "MCP is a query language like SQL"
✅ **CORRECT:** MCP is a protocol (like HTTP). GraphQL is the query language

❌ **WRONG:** "The bot talks directly to Craft CMS"
✅ **CORRECT:** Bot → MCP Wrapper → GraphQL API → Craft CMS (4 layers)

### Technical Q&A for Developers

**Q: Where is the actual tool execution code?**
A: There is no "tool execution code" per se. The `McpServerService::executeToolCall()` method dynamically builds a GraphQL query string based on the tool name and arguments, then executes it against Craft's GraphQL API. All tools use the same code path.

**Q: Can I add custom logic to a tool?**
A: Yes, but you need to modify `McpServerService`. You could add a switch statement in `executeToolCall()` to handle specific tool names differently:
```php
if ($toolName === 'query_officeLocations') {
    // Custom logic for offices
    return $this->customOfficeQuery($arguments);
}
// Default: auto-generated GraphQL query
return $this->defaultToolExecution($toolName, $arguments);
```

**Q: How does the plugin know which fields to include in GraphQL queries?**
A: During introspection, it reads the GraphQL schema's field definitions. It includes all scalar fields (string, int, etc.) and one level deep for relations. Matrix/complex fields are included but may need custom formatting.

**Q: What if my GraphQL schema has custom queries (not just `entries`)?**
A: Currently, the plugin only generates tools for `entries` queries. For custom queries, you'd need to manually add tool definitions in `ManifestBuilderService::generateCustomTools()`.

**Q: Is there a performance difference between 10 tools and 100 tools?**
A: Minimal. All tools are loaded into memory at once (~1MB for 100 tools). The bottleneck is always the GraphQL query execution, not the number of tool definitions.

**Q: Can multiple AI clients use the same schema?**
A: Yes! Multiple Botpress bots, Claude Desktop instances, etc. can all use the same `schemaHandle` and token. The plugin is stateless.

**Q: What happens if two requests hit the endpoint at the exact same time?**
A: PHP-FPM handles this with separate worker processes. Each request gets its own process/memory space. No race conditions.

**Q: Can I use this with Craft CMS 4?**
A: With modifications. Craft 4's GraphQL API is slightly different. You'd need to update the introspection query and possibly field type mappings.

## 🎓 Technical Deep Dive (For Developers)

### What is MCP?

**Model Context Protocol** is an open standard created by Anthropic (makers of Claude) for AI-to-data connections.

- **Think of it as:** "USB-C for AI" or "ODBC for LLMs"
- **Purpose:** Standardized way for AI assistants to discover and use external tools/data
- **Specification:** JSON-RPC 2.0 over HTTP/SSE with defined message schemas
- **Key concepts:**
  - **Tools:** Actions AI can perform (like "query content")
  - **Resources:** Data sources AI can read (like "knowledge base")
  - **Prompts:** Reusable prompt templates

### Why MCP Matters for Developers

**Without MCP (Traditional Approach):**
```
AI Platform → Custom API → Custom Parser → CMS
     ↓            ↓             ↓           ↓
  Different    Different     Different   Different
   for each    endpoint      response    for each
  AI vendor    format        format      platform
```

**With MCP (Standardized Approach):**
```
AI Platform → MCP Protocol → MCP Server → CMS
     ↓              ↓             ↓         ↓
  Standard     JSON-RPC 2.0   Standard   Any CMS
  across all                  interface
  vendors
```

**Developer Benefits:**
- ✅ **Write once, use everywhere**: Same MCP server works with Claude, ChatGPT, Airia, etc.
- ✅ **Self-documenting**: Tools include JSON Schema definitions
- ✅ **Type safety**: Strong typing for inputs/outputs
- ✅ **Protocol-level features**: Built-in streaming, progress updates, cancellation
- ✅ **Discovery**: AI can introspect capabilities without hardcoding

### Why Not Just Use GraphQL Directly?

**You could**, but MCP adds:
1. **Self-discovery:** AI can ask "what can I do?" and get tool definitions
2. **Schema validation:** Proper JSON Schema for inputs/outputs
3. **Standard protocol:** Works across any MCP-compatible AI
4. **Tool descriptions:** Human-readable descriptions for AI decision-making
5. **Abstraction layer:** Hide CMS complexity from AI
6. **Multi-source aggregation:** Combine data from multiple backends

**What happens:**
1. Queries GraphQL's `__schema` endpoint
2. Parses all queryable types (sections)
3. Extracts field definitions for each type
4. Maps Craft field types to JSON Schema types:
   - `PlainText` → `string`
   - `Number` → `integer`/`number`
   - `Date` → `datetime`
   - `Entries`/`Assets` → `relation` (with source handles)
   - `Lightswitch` → `boolean`
   - `Matrix` → `array` of objects
5. Generates tool definitions with proper schemas
6. Caches result to filesystem

private function handleCustomTool(string $toolName, array $args): array
{
    if ($toolName === 'search_experts_by_skill') {
        return $this->searchExpertsBySkill($args);
    }
    
    // Fall back to default handler
    return $this->handleStandardTool($toolName, $args);
}

private function searchExpertsBySkill(array $args): array
{
    $skill = $args['skill'];
    $location = $args['location'] ?? null;
    
    // Custom GraphQL query with complex filtering
    $query = <<<GQL
    query {
      entries(section: "people") {
        ... on people_people_Entry {
          id
          title
          certifications
          skills
          officeLocation {
            ... on officeLocations_officeLocations_Entry {
              city
              state
            }
          }
        }
      }
    }
    GQL;
    
    $result = $this->executeGraphQL($query);
    
    // Post-process in PHP (filter by skill)
    $filtered = array_filter($result['data']['entries'], function($person) use ($skill, $location) {
        $hasSkill = in_array($skill, $person['skills'] ?? []);
        $matchesLocation = !$location || $person['officeLocation']['city'] === $location;
        return $hasSkill && $matchesLocation;
    });
    
    return ['entries' => array_values($filtered)];
}

### Why JSON-RPC 2.0?

**Pros:**
- ✅ Simple, well-defined spec
- ✅ Language-agnostic
- ✅ Supports batch requests
- ✅ Built-in error handling
- ✅ Easy to implement in any language

**Cons:**
- ❌ More verbose than REST
- ❌ Less familiar to most developers
- ❌ Requires JSON parsing for every request

**Alternatives Considered:**
- REST: Rejected - no standard for tool discovery
- GraphQL: Rejected - would expose Craft's schema directly
- gRPC: Rejected - complexity, not web-friendly

### Why File-based Caching?

**Current Implementation:**
```php
// storage/runtime/mcp/manifest-{schemaHandle}.json
```

**Pros:**
- ✅ Zero configuration
- ✅ Survives PHP-FPM restarts
- ✅ Easy to inspect/debug
- ✅ Works on any hosting

**Cons:**
- ❌ Not distributed (doesn't work across multiple servers)
- ❌ File I/O slower than Redis/Memcached
- ❌ No TTL support (manual invalidation only)

**Future: Redis Caching (for multi-server)**
```php
// config/mcpwrapper.php
return [
    'cacheDriver' => 'redis', // or 'file'
    'cacheTtl' => 3600, // 1 hour
];
```

- ✅ Auto-updates when sections change
- ✅ Less configuration to maintain
- ❌ Less control over exposed fields
- ❌ Harder to customize tool descriptions

**Recommendation:** Introspection for most use cases, manual for custom tools

### Security Model

**Three-layer security:**

1. **GraphQL Schema Permissions**
   - Controls which sections/fields are accessible
   - Set in Craft CP → GraphQL → Schemas

2. **Token-based Authentication**
   - Each schema has unique bearer token
   - Different tokens for different use cases (public, internal, AI)

3. **Read-only by Design**
   - MCP Wrapper only exposes **query** operations
   - No mutations (create/update/delete)
   - Content stays safe

**Example: AI Schema for Chatbots**
```php
'ai' => getenv('GQL_AI_TOKEN') // Limited to: Services, News, Offices

## 💡 FAQs for Your Demo

**Q: Is this secure? Can the AI modify content?**
A: Read-only by design. The MCP wrapper only exposes query operations, no mutations. GraphQL schema controls exactly what's accessible.

**Q: What if our CMS is slow? Will that make the chatbot slow?**
A: The tool definitions are cached. Actual content queries go to CMS in real-time, but most queries are fast (<500ms). You can also implement caching at the GraphQL level if needed.

**Q: Does this work with other CMS platforms?**
A: This specific plugin is for Craft CMS, but the MCP protocol is platform-agnostic. Similar implementations exist for WordPress, Drupal, Contentful, etc.

**Q: Can we use this with ChatGPT or other AI?**
A: Yes! MCP is an open standard. It works with Claude Desktop, ChatGPT (with plugins), Airia, and any custom AI tool that supports MCP.

**Q: What happens if someone asks about content that doesn't exist?**
A: The AI gracefully handles empty results. The bot is instructed to offer alternative searches or contact information.

**Q: Can we limit what the AI can access?**
A: Absolutely. You configure this in the GraphQL schema. For example, you might give the public chatbot access to services and offices, but not draft content or internal documents.

**Q: How much does this cost to run?**
A: The plugin itself is open source (free). You pay for:
- Hosting (already paying for Craft CMS hosting)
- Botpress subscription (based on conversations)
- AI API usage (based on tokens used)

**Q: How long did this take to set up?**
A: Initial setup: ~2 hours (install plugin, configure GraphQL, set up Botpress integration). Ongoing maintenance: zero - it just works.
